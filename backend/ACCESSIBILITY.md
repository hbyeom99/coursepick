# 접근성 정보 로컬 연결

이번 작업은 로컬 소스와 SQL 준비만 수행했다. Supabase 변경, GitHub 업로드, Vercel 배포는 실행하지 않는다.

## 로컬에서 확인하기

기존 방식으로 백엔드와 Vite 개발 서버를 실행한다. 개발 모드에서 장소 응답에 `accessibility_info`가 없거나 null이면 보관 원문에서 생성한 `src/data/accessibilityPreview.json`을 장소 ID로 연결한다. 로컬 화면은 저장 원문에 대한 미리보기이며 Supabase에 해당 열이 추가됐다는 뜻이 아니다.

DB의 `accessibility_info`가 존재하면 로컬 자료보다 우선한다. JSON schemaVersion=1과 시설별 판정/원문을 확인한다. 빈 객체나 잘못된 스키마는 미확인으로 처리하며 로컬 자료로 덮어쓰지 않는다.

개발 전용 자료는 프로덕션 빌드에서 사용하지 않는다. 이후 공개 앱에 반영하려면 DB SQL과 코드 배포를 각각 진행해야 한다.

## 화면과 검색

- 장소 상세의 ‘접근성 시설 정보’에서 시설별 판정·원문·출처·상세 조회일을 확인한다.
- 구성원 메뉴는 기존 유아 동반·반려동물 동반·없음 구성을 유지한다. 접근성 시설 선택 UI는 제공하지 않는다.
- 접근성 키워드 검색에서는 available이며 원문 근거가 있는 시설 정보를 사용한다.
- ‘휠체어 접근’, ‘장애인 화장실’, ‘점자블록’ 등으로 검색할 수 있다. 부정 설명이나 코스 제목에 단어가 있다는 이유로 접근성 조건을 통과시키지 않는다.
- 장소 사이 이동 경로·버스/지하철의 접근성, 영업 여부, 현장 시설 규격과 실제 이용 가능성은 검증하지 않았다. 장소 전체를 ‘무장애 이용 가능’으로 판단하지 않는다.

## DB 변경 준비

`backend/place_accessibility.sql`은 기존 places에 nullable JSONB 열 `accessibility_info`를 추가하고 준비된 장소에만 값을 채운다. 기존 장소/태그/유아/반려동물 정보는 유지한다. 기존 접근성 값이 있는 행은 덮어쓰지 않는다. 원문에서 available인 항목만 검색 태그에 추가한다.

이 SQL은 아직 실행하지 않았다. 실행 전 데이터 백업과 대상/건수 확인이 필요하다. 기존 RLS와 권한을 완화하지 않는다. 적용 후 앱 일반 사용자에게 장소 수정 권한이 없는지도 확인한다.

판정은 휴리스틱으로 제안한 원문 기반 분류이며 운영자/현장 확인이 아니다. 모호한 원문, 상충하는 복수 원문은 review_pending으로 둔다. 원문 공란은 unknown이다. 원문별 contentId·조회일·원천목록 수정일을 보관한다.
