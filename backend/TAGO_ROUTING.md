# 대중교통 계산 설정과 확인 방법

이번 변경은 로컬 코드와 설정만 반영한다. GitHub 업로드, Vercel 설정 변경 및 배포는 실행하지 않았다.

## 계산 순서

1. 각 장소에서 500m 이내 정류장 최대 3개를 조회한다.
2. 출발·도착 정류장에 공통으로 있는 노선을 조회하고 운행 순서에 맞는 직행을 먼저 찾는다.
3. 직행이 없으면 양쪽 정류장을 지나는 노선으로 환승 최대 1회 경로를 찾는다.
4. 후보를 임의로 잘라서 계산하지 않는다. 설정한 범위를 넘으면 탐색 미완료로 안내한다.
5. 노선별 정류장 순서를 유지한다. 순환 노선에서 같은 정류장이 반복돼도 서로 다른 방문 순번을 합치지 않는다.

직행이 있으면 환승보다 우선한다. 따라서 전체 교통망의 최단시간을 보장하지 않는다. 결과의 `searchScope`는 `direct-first` 또는 `up-to-one-transfer`이며 `optimalityGuaranteed`는 false이다.

## 설정

기본값은 `backend/tago_settings.json`에 저장한다. 비밀키는 이 파일에 넣지 않는다.
환경변수 > backend/.env > JSON 기본값 순으로 적용된다. 기존 `TAGO_API_SERVICE_KEY` 설정은 그대로 사용한다.

| JSON 항목 | 환경변수 이름 | 기본값 | 허용 범위 |
|---|---|---:|---:|
| timeout_seconds | TAGO_TIMEOUT_SECONDS | 28초 | 1~60 |
| request_timeout_seconds | TAGO_REQUEST_TIMEOUT_SECONDS | 6초 | 1~10 |
| max_requests | TAGO_MAX_REQUESTS | 96회 | 1~200 |
| max_workers | TAGO_MAX_WORKERS | 4개 | 1~8 |
| max_candidate_routes | TAGO_MAX_CANDIDATE_ROUTES | 80개 | 1~200 |
| cache_ttl_seconds | TAGO_CACHE_TTL_SECONDS | 21600초(6시간) | 0~86400 |
| cache_max_entries | TAGO_CACHE_MAX_ENTRIES | 1024개 | 1~10000 |

28초와96회는 코스 내 모든 구간이 공유하는 조회 예산이다. 후보80개는 구간/도시별 탐색 한도이며, API 페이지 조회도 요청 예산에 포함한다. 여러 사용자의 호출이 합산되는 TAGO 계정 일일 이용량 제한은 별도로 관리해야 한다.

노선·정류장 응답을 서버 프로세스 메모리에서 재사용한다. 프로세스 재시작/서버리스 인스턴스 교체 시 캐시가 비워지며 인스턴스 간 공유되지 않는다. 실시간 도착예정정보는 조회하지 않는다. 설정/코드 반영 후 로컬 서버 재시작이 필요하다.

## 검증

프로젝트 루트에서 `python -m unittest discover -s backend -p test_tago_routes.py -v`를 실행한다. 외부 API나 DB에 연결하지 않는 모의 응답 테스트이다.

실제 부산 구간의 성공 여부와 응답시간은 별도로 로컬 서버에 실제 인증키를 연결해 확인해야 한다. 모의 테스트 통과를 실제 TAGO 경로 검증으로 해석하지 않는다.

## 유지되는 제한

- 버스만 지원하며 도시 간 이동과 지하철은 지원하지 않는다.
- 정류장 ID가 같은 곳에서의 환승만 지원한다. 서로 다른 정류장 사이를 걷는 환승은 제외한다.
- 버스 시속20km, 거리보정1.2배, 정류장당30초와 도보 시속4.5km, 거리보정1.3배로 계산한다.
- 교통상황과 배차·환승 대기시간, 운행일/운행 종료 여부를 반영하지 않는다. 실제 출발시각에 탑승 가능한 경로를 보장하지 않는다.
- 프런트엔드의 기존 '약 ...분 · 대기시간 제외' 표시는 유지한다.
