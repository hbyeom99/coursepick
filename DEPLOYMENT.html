준비된 파일

source/는 GitHub에 반영할 소스입니다. build/는 기존 운영 API 주소로 빌드한 정적 결과이며, 백엔드 배포를 포함하지 않습니다. ZIP에는 source/만 포함합니다. 기존 프로젝트 폴더 전체를 업로드하지 마세요. 실제 환경설정·서버 키·DB 백업·관련 없는 문서는 제외했습니다. 앱에서 사용하는 공개 이미지와 폰트는 포함합니다.

이번 수정

backend/main.py의 장소 목록에 offset/limit을 추가했습니다. 페이지 요청은 최대 500개이며 내부 추천 계산의 전체 목록 조회는 유지합니다. src/services/placeService.ts는 500개씩 최대 3건을 동시에 요청합니다. 기존 Supabase 조회 대체 경로를 유지합니다. 홈·검색의 출발 시간과 여행 인원 입력란 제거도 포함합니다.

검증 결과

  • 운영 API 주소로 Vite 빌드 성공. 현재 서버 전용 키 문자열이 소스·빌드 파일에 포함되지 않음을 검사했습니다.
  • 장소 페이지 서버 범위/마지막 페이지/기존 ID 조회 8개 검사 통과.
  • 프론트엔드 0~21,496개 모의 장소에서 순서·누락·동시 요청 수·중복 검사를 통과했습니다.
  • 실제 DB 읽기 전용 500개 요청 두 건: 475,777 / 465,110 bytes. ID 중복 없음.
  • 대중교통 단위 테스트 14개, 현재 코스 생성 규칙 테스트 19개 통과.
  • 최신 장소 스냅샷의 기본 목록은 21,496개, 전체 JSON 약 20.47MB. 500개 구간 최대 약 0.95MB로 확인했습니다.

추후 실제 배포 순서

  1. Vercel의 기존 프론트·백엔드 프로젝트에서 현재 정상 배포의 URL/버전과 환경변수 설정을 기록합니다. 기존 GitHub 자동 배포가 켜져 있으면 운영 브랜치에 업로드하는 즉시 배포될 수 있으므로, 먼저 별도 준비 브랜치에서 검토합니다.
  2. ZIP을 풀고 source/의 파일을 기존 저장소에 반영합니다. 전체 저장소를 지우거나 기존 배포 설정을 무조건 덮어쓰지 마세요. 이 폴더는 별도 Git 저장소가 아니며 기존 저장소와의 차이 검토는 아직 하지 않았습니다.
  3. 프론트 프로젝트는 저장소 루트, Vite, 빌드 npm run build, 결과 dist를 사용합니다. pnpm 잠금 파일이 있으므로 Vercel의 자동 감지 설치를 유지합니다.
  4. 백엔드 프로젝트의 Root Directory는 backend입니다. main.py의 app을 FastAPI 진입점으로 사용하고 requirements.txt를 설치합니다. backend 파일만 빠뜨리지 않고 함께 반영합니다.
  5. 아래 환경변수를 해당 프로젝트의 Preview와 Production에 확인합니다. .env.example은 이름을 안내하는 양식이며 실제 키는 Vercel 설정에 입력합니다.
  6. 별도 미리보기 배포에서 백엔드 health·장소 목록·로그인·검색·코스 저장·지도·이동수단을 확인합니다. 프론트 미리보기가 새 백엔드 미리보기 주소를 사용하도록 지정하고 해당 프론트 주소를 CORS_ORIGINS에 추가합니다. 카카오 JavaScript 허용 도메인도 테스트 주소를 확인합니다.
  7. 확인 후 백엔드, 프론트 순으로 운영 적용합니다. 기존 도메인을 유지합니다. 실제 휴대폰에서 로그인 유지·검색·코스 저장을 다시 확인합니다.
  8. 문제가 생기면 Vercel에서 기록한 이전 정상 배포로 프론트와 백엔드를 각각 되돌립니다. 이번 준비에는 DB 마이그레이션이 없으므로 DB 복원은 필요하지 않습니다.
